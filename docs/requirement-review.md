# 需求评审：sing-box-webui 集群化（一主多从）

> 状态：评审稿 v0.1（未实现） · 日期：2026-08-10 · 依据：README「未来展望」
> 相关文档：[技术栈与协议选型](./tech-stack-protocol.md) · [集群架构设计](./cluster-architecture.md)

## 1. 原始需求

README「未来展望」原文：

> 集群系统，一主多从。
> 主节点有面板，从节点只有后端。
> 从节点自动向主节点注册。
> 主节点通过 api 控制从节点。
> 通信方式参考 komari。

## 2. 需求解读（5W1H）

| 维度 | 解读 | 备注 |
|---|---|---|
| What | 把单机版 sing-controller 扩展为一主多从的集群控制面：主节点集中管理所有从节点的 sing-box 实例 | 控制面集群，非流量集群 |
| Why | 多台服务器（含 NAT 后的小鸡）统一管理：一个面板看全部节点、集中下发配置、批量重载 | 与 komari 监控集群的动机一致 |
| Where | 主节点：面板 + 集群 Hub（WebSocket 服务端）；从节点：现有 sing-controller 核心 + Agent 模块 | 单二进制演进 |
| Who | 管理员（主面板操作）；从节点机器本身无操作入口（或仅本地 CLI） | 从节点「只有后端」 |
| When | 从节点启动即注册；配置变更即下发；心跳持续在线 | 实时性要求：秒级状态、操作级配置同步 |
| How | 参考 komari：Agent 主动出站连 Master（WebSocket + JSON-RPC 2.0 + Token 认证） | 关键约束：必须 NAT 友好 |

## 3. 关键待澄清问题（阻塞项，需产品拍板）

| # | 问题 | 影响 | 建议默认 |
|---|---|---|---|
| Q1 | **配置归属模型**：从节点的 sing-box 配置以「主节点下发」为准，还是「从节点自治、主节点仅监控/命令」？ | 决定整个数据流方向与冲突处理 | 混合：主节点可下发整包配置（显式覆盖），从节点保留本地管理能力；主节点离线不影响从节点运行 |
| Q2 | **从节点「只有后端」的实现形态**：编译期去掉 webui（二进制瘦身）还是运行时禁用？ | 构建矩阵与发布复杂度 | 运行时禁用（`-webui=false`）+ 可选构建 tag 裁剪，MVP 先运行时禁用 |
| Q3 | **集群规模预期**：几个节点还是几十个？ | Hub 设计（单机瓶颈、是否分片） | 按 50 节点/单主设计，够用且简单 |
| Q4 | **主节点是否同时是代理节点**？ | 部署拓扑 | 主节点独立部署（只跑面板+Hub），也可选配本地 sing-box，架构上不耦合 |
| Q5 | **是否需要多用户/权限隔离**（不同管理员管不同节点）？ | 鉴权模型复杂度 | P1 再做；MVP 单管理员（沿用 -secret 体系） |
| Q6 | **节点分组/批量操作**（按组下发、批量重载）？ | 命令面设计 | P1：节点打标签分组，批量=对组内节点逐个发任务 |
| Q7 | **主节点宕机时从节点行为**：继续服务（推荐）还是停止接受连接？ | 可用性语义 | 从节点配置本地持久化，主节点离线仅丢失「管理」能力，不影响代理服务 |
| Q8 | **通道安全**：公网部署是否需要 TLS 加密（自签/wss）+ 双向认证？ | 安全模型 | 支持 wss（反代或内置自签证书）+ Token；P1 加 mTLS 选项 |
| Q9 | **是否需要流量/连接统计回传**（sing-box service API 已有数据）？ | 面板信息量 | P1：透传节点 sing-box service API（现有 /api/grpc 代理模式），不做聚合存储 |
| Q10 | **从节点是否可能被「接管执行任意命令」**（komari 有 Web Terminal）？ | 安全边界 | 控制面默认**不提供**任意命令执行；仅白名单操作（配置/重载/状态）。Terminal 类能力 P2 且需二次确认 |

## 4. 需求分级

### P0（MVP，必须）
- 一主 + 至少一从（从节点可在 NAT 后）完成闭环：注册 → 面板显示在线 → 查看/编辑从节点配置 → 下发 → 重载生效
- 从节点自动注册：预生成 Token 部署，Agent 启动即连接（参考 komari Token 机制）
- 心跳 + 状态上报：在线/离线、sing-box 运行状态、配置 hash（面板显示同步状态）
- 主节点下发配置 & 触发重载（复用现有 store 校验管线与 reload 自动适配）
- 从节点运行不带 webui（运行时禁用）
- 单机模式零回归（现有部署完全兼容）

### P1（近期）
- 多节点管理、节点分组、批量下发/重载
- 配置冲突检测（hash 漂移告警 + 覆盖确认）
- 透传从节点 sing-box service API（连接数/流量实时视图）
- 操作审计日志（谁、何时、对哪个节点做了什么）

### P2（远期）
- 模板变量（按节点替换 listen/端口/域名）
- 计划任务（定时重载/更新规则集）
- Web Terminal / 任意命令（安全评审后，二次确认）
- 多主（高可用）或 Hub 分片

## 5. 非目标（明确不做）

- **不做流量中继**：master 不转发代理流量，数据面在 sing-box 节点间直连
- **不做监控告警**（CPU/内存时序存储）：komari 本体已解决，可共存部署；本系统只关心 sing-box 配置与运行状态
- **不做从节点自动发现**（局域网广播等）：只做「Token 配置后主动注册」
- **不做多租户计费**（用户量/流量计费）：与用户池/入站管理解耦

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Token 泄露 → 节点被恶意接管 | 高 | Token 随机高强度 + 仅握手一次 + 支持轮换；wss 加密；节点侧命令白名单 |
| 配置覆盖导致从节点本地修改丢失 | 中高 | 下发前 hash 比对 + 显式确认；本地保留 .bak（现有管线已有）；审计 |
| 网络分区（主-从断连） | 中 | 从节点配置本地化，断连不影响服务；Agent 指数退避重连；主面板标记离线不误判 |
| 主节点单点 | 中 | MVP 接受单主；P2 多主；主节点可轻量多部署（仅 Hub + 面板） |
| 命令通道被中间人篡改 | 中 | wss/TLS + Token；响应签名可选（P1） |
| 现有单机功能回归 | 高 | 集群模块与现有代码物理隔离（新包 + 接口适配层），单机路径不改；回归测试守门 |

## 7. 验收标准（草案）

1. 全新部署一台主 + 一台 NAT 后从节点，按文档 5 分钟内完成注册并在线
2. 主面板修改从节点 sing-box 配置（增/删入站）→ 下发 → 从节点实例重载生效，无人工登录从节点
3. 拔掉主-从网络 10 分钟：从节点代理服务持续可用；恢复后自动重连并补报状态
4. 现有单机模式（无集群配置）启动、管理、重载行为与 v0.10.0 完全一致
5. `go test ./...` 全绿；集群模块单测覆盖注册/心跳/任务/重连核心路径

## 8. 建议

- **先按 Q1 混合模型 + komari 通信范式做 P0 原型**（单从节点闭环），验证通道与配置下发链路后再铺开多节点
- 从节点复用现有 sing-controller 二进制（运行时禁 webui），**不新建独立 Agent 二进制**，控制维护成本
- 集群通道默认关闭（无 cluster 配置即纯单机），保证兼容性
